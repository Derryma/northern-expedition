# 事件卡系統重建工作紀錄

> **歷史工作紀錄。** 本文保留重建過程與舊的「四張／四家依序回應」設計。現行版本已改為
> 每三回合只抽一張共享事件，隨機選出符合條件的受影響陣營；該陣營回應後，事件在全局完成。
> 現行卡表與規則以 `cards/README.md` 及兩份 cards JSON 為準。

2026-08-14。上一份《事件卡系統移除工作紀錄》把舊的 116＋19 張事件卡整套拆掉，
這一份記錄的是重建：資料改由《1926-1928 全球大事事件卡設計稿_v2》第一至六區塊產出，
前端不做「抽卡」動作，改成每三回合直接跳出一張民國老報紙。

## 一、規則

- **每三回合**（第 3、6、9⋯回合）自動抽 **4 張**事件卡。
- **抽出**順序固定 **奉 → 直 → 五 → 國**：第一張歸奉系、第二張歸直系，依此類推。
  這個歸屬會顯示在報紙上，也決定表態卡的建議回應順序。
- **四張全部結算完畢後**，該回合的金錢、工廠、債務才會結算，玩家才能開始行動。
- 抽過的卡不再洗回牌庫：29 張撐約 7 個週期，抽完就不再發報。

### 回應順序（`draw_rules.strict_response_order = true`，現行）

回應嚴格照 **奉 → 直 → 五 → 國**。一般事件由抽到該卡的玩家回應；需要所有勢力表態的卡
（〈亞克斯搜查案〉〈非戰公約〉）以抽到該卡的玩家為第一個回覆者，其餘照上述順序輪流，
**每一家的選擇只作用在自己身上**，同一張卡全部回應完才換下一張。

順序鎖住之後會有「輪到的不是我現在這一家」的問題，所以**報紙右上角自帶一個陣營選擇欄**：
下拉選單列出四家，該回應的那一家後面標「←應由此家回應」，選過去之後按鈕就可以點，
主畫面上方的陣營選單也會同步跟著換。**四張全部結算完，報紙整份清空、這個選擇欄一併消失**，
換陣營回歸主畫面上方的選單，直到下次發報才再出現。

另有一套寬鬆模式留在程式裡：把 `strict_response_order` 改成 `false`，單純事件變成任何一家
點閱都算數、表態卡四家不拘先後。引擎與前端都認這個旗標，改資料就會切換。

## 二、資料

`cards/data/event_cards.json`（版本 `experimental-1.1`，38 張）。內容全部取自
`事件卡工作日誌/1926-1928 全球大事事件卡設計稿_v3.md` 的第一至八區塊：
政治 7、外交 7、文化 4、藝術 4、體育 3、商業 4、學術 4、科技 5。
第九區塊之後（中國藝文／學術／商業界共 15 張）尚未收錄。

v3 相對 v2 只有兩處差異，兩處都已跟進：〈棉花俱樂部〉補上「控制上海或天津者此卡才會
進入牌庫」的進入條件；〈官費留學生〉的效果從「付 15 元、3 回合後生效」改成「解鎖
〈公費留學生〉功能卡」。

每張卡的欄位：

| 欄位 | 內容 |
| --- | --- |
| `id` / `ref` / `name` | 卡片代號、設計稿編號（如 `2.3`）、卡名 |
| `category` | 沿用舊四分類：`foreign_power`／`economic`／`npc_or_other_force`／`security` |
| `power_note` | 設計稿類別後面的括號註記（日、蘇、英／蘇⋯） |
| `effect` | 設計稿的效果全文，原樣搬進來，報紙上的「本報附誌」就是它 |
| `condition` | 設計稿有寫「條件」的兩張才有 |
| `newspaper.headline` / `newspaper.paragraphs` | 新聞仿寫的標題與正文段落 |
| `resolution` | `acknowledge`（我知道了）或 `choice`（附 `options`，每個選項有 `label`、`effect_text`、`apply`） |
| `entry_condition` | 進入牌庫的條件，例如 `{"controls_province": "江蘇"}`、`{"controls_cities_any": ["shanghai"]}` |
| `apply` | 引擎接得住的機械化效果；接不住的寫在 `apply.notes`，報紙上以「※」標出 |

### 進入條件與 scope

四張卡帶 `entry_condition`：〈棉花俱樂部〉（控制上海或天津）、〈中央研究院〉（控制江蘇）、
〈殷墟第一鏟〉（控制河南）、〈跨洋長途電話〉（控制上海）。抽卡時只從「現在有人符合條件」的
卡裡抽；抽到之後如果排到的那一家不符合，會改發給符合的人（照 奉 → 直 → 五 → 國 取第一個）。
沒有人符合的卡就留在池子裡等局勢改變。

`resolution.scope` 決定效果發給誰、由誰回應：`all_players` 是全場（預設），`drawer` 只發給
抽到的那一家、也只有那一家要回應。〈中央研究院〉〈跨洋長途電話〉〈殷墟第一鏟〉都是 `drawer`。

## 三、報紙格式

`frontend/index.html` 多了 `#newspaperBackdrop` 一層遮罩，樣式在 `frontend/styles.css`
的 `.newspaper*` 一段，內容由 `frontend/app.js` 的 `newspaperMarkup()` 產生。由上而下：

報頭左側是大字「民國報」（字距拉開、雙線分隔），右側小字寫卡片名稱。往下一列是日期與
「本期第 N 則／共 4 則」的進度。再往下是圖片預留區——目前畫的是仿網點印刷的灰框，
中間寫「［圖片待補］」加卡片代號，之後把圖檔以卡片 `id` 命名丟進去即可。圖片區下面
緊接新聞標題，標題下是正文，兩者都用標楷體（`"標楷體", "DFKai-SB", "BiauKai", KaiTi`，
找不到才退回襯線字體）。正文下面是「本報附誌」，寫這張卡對遊戲做了什麼；需要表態的卡
會再多一欄「行動選項」，逐條列出每個選項的後果。最底下是回應區：單純事件只有一顆
「我知道了」，需要表態的卡則列出行動按鈕；輪不到你的時候按鈕反灰並顯示「等待某某回應」，
輪到了就顯示「請閣下裁示」。

報頭右側除了卡名之外還有一個**陣營選擇欄**（`[data-newspaper-faction]`），只在報紙開著時
存在，用來把視角切到該回應的那一家；它與主畫面的 `#playerSelect` 共用 `switchFaction()`，
兩邊永遠同步。報紙收起時 `renderNewspaper()` 會把整份 `innerHTML` 清空，選擇欄隨之消失。

設計稿沿用 Markdown 的 `**粗體**`，報紙上會轉成真的粗體，不會露出星號。

## 四、引擎

`backend/card_engine.py`：

- `next_turn()` 拆成兩半。回合數一到，`_start_event_cycle()` 抽四張、排好回應佇列，
  然後**直接回傳** `{"turn": {"awaiting_events": True}}`——本回合的經濟完全沒跑。
- `_finish_turn()` 是原本 `next_turn()` 的後半段（經濟結算、timed effects、卡池同步）。
  它只在四張都回應完之後才被 `respond_event()` 呼叫。
- `pending_event_view()` 給前端看的當前狀態：第幾則、卡片全文、抽到者、還缺誰
  （`pending_responders`），以及 `strict_order`、`needs_every_faction` 兩個旗標。
- `respond_event(player, choice)` 記錄回應、套用效果；一張結完推進索引，四張結完清空
  `pending_events` 並呼叫 `_finish_turn()`。嚴格模式下檢查是否輪到該玩家，寬鬆模式下
  只擋「同一家重複回應同一張卡」。
- 狀態新增 `event_pool`、`event_history`、`pending_events`、`perk_suspensions`、
  `bank_bans`、`bank_limit_multipliers`、`function_card_overrides`。

`backend/server.py` 多了 `/api/respond-event`；`bootstrap()` 的 `cards` 多了 `event` 一組，
所以前端不必另外抓檔案。`backend/data_store.py` 重新載入 `cards/data/event_cards.json`。

### 第二層選擇（follow_up）

選項可以再帶一層 `follow_up`：玩家點下該選項後，報紙的按鈕列會換成第二排，選完才送出。
目前只有〈殷墟第一鏟〉的「售與洋商」用到——第二排是日、蘇、英、美、法五顆買家按鈕，
外加一顆「改選」可以退回第一層。後端 `respond_event(player, choice, follow_up)` 會驗證
第二層的選擇，沒選就擋下並顯示提示。

### 中央研究院的狀態機

這張卡不是一次性的加成，而是一個跟著江蘇跑的狀態，記在玩家的 `academia_sinica`
（`holder` / `disqualified`）：

- **收編**（抽到並回應）之後，只要**控制江蘇**：每回合工業點 +5，且〈盜賣文物〉從你的
  卡池整個清空、手上那幾張也打不出來。
- **丟掉江蘇**：加成停止，〈盜賣文物〉洗回卡池（張數回到 3）。奪回江蘇則兩者都回來。
- **永久失效**有兩個觸發點：在離開江蘇期間**打出過〈盜賣文物〉**，或在任何時候選過
  〈殷墟第一鏟〉的**「售與洋商」**。一旦失效，`disqualified` 就再也不會翻回來，
  之後奪回江蘇、甚至重新抽到這張卡都不會恢復。

`perk_suspension` 現在不限列強 perk：任何功能卡都能被按住，被按住的卡會立刻從牌庫收走
（手上那幾張留著，但打出時會被 `_validate_card_use` 擋下並說明是哪張事件卡造成的），
`turns` 寫 `null` 就是無期限（中央研究院把〈盜賣文物〉永久收走）。

### 住在前端的效果

有兩張卡的效果落在前端的部隊與將領樹上，由 `applyFrontendEventEffects()` 在你按下回應
按鈕、後端把該卡結算完之後執行：〈五月的政變潮〉替所有玩家的大帥與嫡系（忠誠不變）將領
的部隊各兵種 +1 營（受 100 戰力上限限制），〈貝爾福宣言〉替每位玩家隨機挑一位可變忠誠
將領 +1。另有兩張靠 `timed_flags` 傳到前端：〈非戰公約〉的停戰會擋下移入他方領地與
主動攻擊，〈泳渡海峽的女子〉的三回合窗口讓全軍都吃〈進口盤尼西林〉那套戰後傷兵歸隊。

`perk_suspension` 是接在 `_sync_foreign_deck_cards()` 上的：被停權的卡 `desired` 直接歸零，
還沒抽到的會被收回去，到期後下一次同步又自動洗回來。`card_overrides` 接在
`_card_template()` 上，所以〈盜賣文物〉的收益改寫對所有讀卡的路徑一次生效。

### 8.1 新機制

**`tags` 欄位＋事件卡封鎖（`event_locks`）。** 封鎖與移除從此是兩件事：

- **封鎖**：卡片留在 `event_pool` 裡，封鎖期間 `_start_event_cycle` 跳過它，到期自動又抽得到。
- **移除**：從 `event_pool` 拿掉，不再回來（抽過的卡就是這樣）。

一條封鎖可以指名卡片（`cards`），也可以用標籤＋列強整批封鎖（`tags` + `powers`）。
`power_note` 允許寫成「蘇／德」，`_event_powers()` 會拆開比對。
payload 欄位：`event_lock`（掛封鎖）、`event_unlock`（提前解封）。

**`event_pool_add`。** 取代舊的「抽中機率 +X%」。`event_pool` 允許同一個 id 出現多次，
多一張就是多一份被抽中的機會；`_start_event_cycle` 同一輪不會抽到同一張兩次。

語意是「**每一張**符合的卡各加 N 張」，不是從符合的卡裡挑一張加——
`tags=["軍事"], powers=["日"], copies=1` 的意思是資料檔裡每一張日本 [軍事] 事件卡都各多一張。
指定不到任何卡時**不會假裝成功**，`applied` 會回報 `note: "no matching event cards in data"`。

### 11.1 交戰判定怎麼做的

後端沒有部隊——部隊的位置與交戰狀態都住在 `frontend/app.js`：

- `army.cellKey` → `provinceForArmy(army)` 得到它在哪一省
- `activeBattleForArmy(army)` 查 `activeBattles` 裡 status 為 `pending` / `ongoing` 的場次

所以判定放在前端、結論送給後端，走的是 `riot_garrisons` / `city_garrisons` 那條既有通道：

```js
function contestedProvinces() {          // frontend/app.js
  const provinces = new Set();
  for (const army of allArmies()) {
    if (army?.status === "jailed") continue;
    if (!activeBattleForArmy(army)) continue;   // 沒在交戰就跳過
    const province = provinceForArmy(army);     // 所在地格 → 省份
    if (province) provinces.add(province);
  }
  return [...provinces];
}
```

隨 `next_turn` 送出 → `server.py` 轉給 `ENGINE.next_turn(contested_provinces=...)` →
`set_contested_provinces()` 收下。後端只負責「拿到清單之後怎麼算」：
`_province_combat_penalty()` 在 `_city_economy_for()` 算城市產出時把減損扣掉。
全部脫離接觸後前端回報空清單，減損立即解除。

### 10.7：報導少一段

使用者已大幅改寫），逐卡比對 59 張卡的效果、條件、報紙標題與**每一段**內文。
只有一處出入：10.7 的報紙在 JSON 裡有 6 段、稿裡 5 段——使用者刪掉了我寫的
收尾那段「又按：蔡、陳、李三君，十年前同在此樓共事……」。已把 JSON 砍到 5 段。

### 9.5：真正的坑不在文字，在 fallback

先把三張分支卡的狀態對照表 dump 出來，確認方向沒有反：

```
9.5  《新月》月刊  探測=free_china_educators  未抽出→加張 / 已抽出→延長
10.1 昆明湖        探測=confucian_revival     未抽出→加張 / 已抽出→擴大免疫省份
10.3 《古史辨》     探測=confucian_revival     未抽出→封鎖 / 已抽出→護持失效
```

方向是對的。但翻 `card_engine.py` 時發現真正的問題：

```python
chosen = branch.get(key) or branch.get("otherwise")   # ← 就是這行
```

只要某張卡沒定義該狀態的分支，就會**悄悄改跑「未抽出」那一支**。
目標卡明明已經抽出了，引擎卻去執行「還沒抽出時才合理」的加張或封鎖——
這正是使用者問的語意顛倒，而且不會留下任何跡象。

改成三種狀態各走各的、**不做 fallback**；沒定義就是沒效果，並在 `applied`
裡回報 `has_branch: false`：

```python
key = "if_active" if (drawn and active) else ("if_drawn" if drawn else "otherwise")
chosen = branch.get(key)
applied.append({"kind": "conditional_branch", "probe": probe,
                "drawn": drawn, "active": active, "chosen": key,
                "has_branch": chosen is not None})
```

### 9.5 的三種狀態怎麼分

設計稿 v5 原文寫得很清楚：「若已抽出（**無論效果是否仍生效**），則改為將該效果
再延長 5 回合——因為一次性卡抽過就不會再出現，加張沒有意義。」
所以 `if_drawn` 與 `if_active` 掛**同一個** `extend_effect`。
效果已散時沒有東西可延長，`extend_effect` 回報 `entries: 0`——空轉但誠實，

## 十六、2026-08-19：貿易出口的加成改為增量

### 起因

使用者要求找出所有影響對美／對英貿易出口的事件卡，把「將貿易收入增加**至** `$30`」
這類寫死的句型全部改成「將貿易收入**增加** `$10`」——以增量取代寫死的數字上限。

### 找到兩張

掃 `event_cards.json` 裡所有動到 `trade_export_*` 的 `card_overrides`：

| 卡 | 影響對象 | 原本 | 期限 |
| --- | --- | --- | --- |
| 4.3 杜蘭朵公主 | 蘇／英／法／美（**不含日本**） | `cash_gain: 30` | 2 回合 |
| 9.4 國立藝術院 | 日／蘇／英／法／美（全五張） | `cash_gain: 30` | 永久 |

只有這兩張。1.7 胡佛當選雖然提到「以貿易代替干預」，但那是敘述，
它動的是 [軍事] 事件封鎖與美國戰鬥 perk，沒有碰貿易出口的收益。

### 寫死的絕對值為什麼是 bug 而不只是寫法問題

`_card_template()` 舊的實作是 `card.update(override["fields"])`——**後蓋前**。
兩張卡都生效時，後生效的那張只是把同一個 `30` 再蓋一次，
第二份加成完全消失。玩家看卡面會以為兩份加成該疊起來，實際上永遠是 30，
而且沒有任何提示。這就是使用者說的「嚴格寫死的數字加成上限」。

### 做法

`card_overrides` 新增 `field_deltas`，與既有的 `fields` 並存：

```python
card.update(override.get("fields") or {})                  # 絕對值：後蓋前
for field, amount in (override.get("field_deltas") or {}).items():
    deltas[field] = deltas.get(field, 0) + int(amount)     # 增量：累加
...
for field, amount in deltas.items():
    card[field] = int(card.get(field, 0)) + amount         # 以原始數字為基準
```

增量一律以卡片原始數字為基準加上去，所以**生效先後不影響結果**。
有期限的那份到期自動退場，剩下的增量照算。

兩張卡的 9 個 override 全部由 `fields: {cash_gain: 30}` 改為
`field_deltas: {cash_gain: 10}`，卡面文字同步改成「現金**增加** `$10`」。

| --- | --- | --- | --- | --- |

| 對日本 | $20 | — | +$10 | **$30** |

## 十八、2026-08-19：報紙效果欄的排版修正

### 兩個症狀，同一個根

使用者回報效果欄「字會在奇怪的地方跳掉或換行」「欄位中央有奇怪的分隔線」。
把報紙元件單獨渲染出來截圖一看，兩個症狀出自同一行 CSS：

```css
.newspaper-effect b { display: block; letter-spacing: 4px; border-bottom: 1px solid #b4a482; }
```

這條本來是要修飾「本 報 附 誌」那個標題。問題是 `newspaperInline()` 會把效果文字裡的
`**粗體**` 轉成 `<b>`，於是**每一個行內粗體都變成整行區塊、還各自帶一條底線**。

〈杜蘭朵公主〉的效果因此被切成三段：

```
歐洲與美國一時盛行中國風⋯
2  回  合                      ← 整行 + 一條橫線
內：所有人〈對蘇／對英／對法／對美貿易出口〉每次現金
增  加                          ← 整行 + 一條橫線
$10，且〈盜賣文物〉收益⋯
```

「2 回合**內**」的「內」被推到下一行，「增加」被抽成獨立一行——
這就是「字跳掉」；那兩條橫線就是「欄位中央的分隔線」。

### 修法

1. 標題改用自己的 class `.newspaper-effect-title`，區塊樣式與底線只掛在它身上。
   `.newspaper-effect b` 改成純粹的行內粗體（`display: inline`、字距正常、無邊框）。
2. 條列改成真正的 `<ul>`。原本的拆行規則是 `/\s+-\s+(?=\*\*)/`——
   只認「連字號後面緊接粗體」的條目，所以〈東方會議〉那種
   「- 對日關係 ≥3 者：⋯」完全沒被拆開，四條規則擠成一整段跑馬燈。
   改成 `/\s+-\s+/`，並加上懸掛縮排與 `・` 項目符號。
3. 效果欄改為靠左排（正文段落維持兩端對齊）。這一欄夾雜中文與 `$20～40`、`≥6`
   之類不可斷開的西文串，兩端對齊時排不下的西文串會被推到下一行、留下一整排空隙，
   看起來也像字跳掉。
4. 效果文字裡的換行改為段落界線，讓 11.5 的收尾句「報紙依判定結果擇一刊出」
   不再黏在最後一個條目後面。
5. 「行 動 選 項」欄同步改用同一套標題 class 與條列樣式。

### 順手抓到的資料問題

為了守住第 2 點的拆行規則，加了 `NewspaperEffectTextTests`（4 項），
其中一條檢查「不准用半形 `-` 當減號」——**一寫完就抓到三張卡**：
1.4 一黨之國、3.3 火燒紅蓮寺、11.2 南洋兄弟與英美煙草，
都寫成「關係 -1」而不是全場慣用的全形減號 `−1`。
雖然現行的拆行規則要求連字號**兩側**都有空白、這三處剛好逃過一劫，
但這是等著出事的地雷。已一併正規化（JSON 與設計稿 v5 各改 3 / 6 處）。

另外兩條守門：`**` 與反引號必須成對——落單會吃掉後面整段文字。

這次是 CSS／標記層的修正，Python 測試碰不到畫面。
所以另外寫了一支渲染治具 `/tmp/shot.py`：從 `app.js` 原地切出

## 二十五、2026-08-19：〈殷墟第一鏟〉的免疫擴及 security 事件卡

依裁示把「科學發掘」的治安免疫從「暴動類功能卡」擴大到**也涵蓋 security 類事件卡**。

### 實際上擋的是什麼

先把 5 張 security 事件卡看過一遍，會傷到城市的其實只有兩張，而且都走同一個機制：

| 卡 | 對城市做什麼 |
| --- | --- |
| 9.3 革命文學論戰 | `student_unrest`：隨機 2 座四／五級大城，3 回合產出減半 |
| 10.7 北京大學共運 | `student_unrest`：同上，2 回合 |
| 5.3 長數之爭 | 沒有效果，純新聞 |
| 7.4 黴菌與傷兵 | 只解鎖〈進口盤尼西林〉，不碰城市 |
| 10.1 昆明湖 | 分支卡，不碰城市 |

所以「免疫 security 事件卡」落到實作上，就是**受保護的省份不得成為學潮的目標**。

### 做法

`blocked_mechanics` 加上 `security_event`，並在 `_student_unrest_candidates()`
過濾候選城市：

```python
if self._gang_riot_shielded(player, city.get("province"), "security_event"):
    continue
```

**免疫的語意是「根本挑不到」，不是「挑中之後不痛」**——整省排除在候選名單之外。
這一點很重要：若改成挑中後再免疫，等於白白消耗掉學潮的兩個名額，
其他省份反而變安全，那是另一回事。

順帶把「沒得挑」的回報講清楚：`applied` 現在會帶 `shielded_provinces`，
分得出來是「被免疫擋掉」還是「本來就沒有夠格的城」。

其他省照舊、**免疫是發給打出那張卡的玩家而不是綁在省份上**（河南易主後新主沒保護）、
以及 9.3 與 10.7 兩張都吃這條——不能只擋其中一張。

## 列強懲戒通用機制（第 12 節）

《可重複抽取事件卡》最前面的幾張都是同一個骨架：日本（或別的列強）因為
邦交惡化而動手，形式分三種——**佔地、封水、轟炸**。與其一張一張寫，
這次先把共通機制做出來，卡片只負責宣告「哪一國、哪一類、範圍是什麼」。

### 可重複抽取

`repeatable: true` 的卡抽完不進 `event_locks`，留在池子裡還會再抽到；
沒有這個旗標的卡一律維持「只能抽一次」。第 12 節四張全部標了這個旗標。

### 三類懲戒

新檔 `backend/foreign_punishment.py`，`PunishmentBook` 掛在 `GameEngine` 上：

| 類別 | 範圍 | 產出 | 傷害（僅敵對時） |
| --- | --- | --- | --- |
| `ground_occupation` | 省份 | 境內城市歸零 | 部隊戰力 −40%、靠港砲艇 −40% |
| `water_blockade` | 水域 | 河港／鄰接海港歸零 | 艦隊生命 −50%、鄰接港口駐軍 −30% |
| `air_raid` | 動態五城 | 五城歸零 | 駐軍 −30% 並逐出城、靠港艦隊 −50% |

共通規則：

* **解除**：關係修好到非敵對（`> −4`）的**下一回合**才解除。佔領解除後
  土地變無主，原勢力要重新佔領；演習（`drill_turns`）則原封不動歸還。
* **演習不是懲戒**：有固定回合數，**不造成任何傷害**。
* **每玩家封鎖**：同一張懲戒卡對同一玩家生效期間對他封鎖，但**不同玩家
  可以同時吃到同一張**。這條寫在 `_event_eligible_players()` 裡。
* **轟炸目標是動態的**：城市易主就換一座遞補，永遠盯著最大的五座。
* **重建**：轟炸解除後每座城要 `3` 回合才復工，中途都算產出歸零。

## 日蘇重疊區、最後通牒、租界管制

### 忠誠度自動化（補上先前的死角）

`pending_frontend_effects` 這個佇列先前**只有懲戒傷害一種 kind 有人消費**，
`loyalty_all`（1.8 日本承認北京政府、10.8 復興儒學，以及〈成立官辦廣播電台〉
在事件卡路徑上的放大）進了佇列就沒人理，等於機制寫了沒生效。

改法不是補一個 if，是把消費端改成**登記制**：`PENDING_EFFECT_HANDLERS` 一個
kind 一個處理器，沒登記的 kind 會在主控台 `console.warn` 叫出來，然後照樣銷帳
（免得無限累積）。這樣下次再有人加 kind 而忘了接前端，會立刻看得見。

### 日蘇重疊區開戰判定

`PunishmentBook.open()` 的先來後到多了一個例外：新舊兩筆佔領的國家若是
`{jp, su}`，重疊的省要打一仗。

* **以省為單位**判定，衝突兩省就擲兩次、兩個結果。
* 勝率蘇聯 `60%`、日本 `40%`。
* **戰敗方只輸掉重疊的那一省**，自己其餘的省照舊佔著。
* 判完當下就結算土地歸屬與傷害，並在同一回合補刊戰況報導。

### 三重傷害疊加

設計稿寫的是「相較初始狀態剩餘 10%／50%」，所以是**以初始值為基準相加**，
不是逐次相乘（相乘會得到 32.4%／54%，與設計稿不符）：

| 情境 | 累計 | 剩餘 |
| --- | --- | --- |
| 日懲戒 → 戰火 → 蘇勝再打擊 | 40 ＋ 10 ＋ 40 | **10%** |
| 日懲戒 → 戰火 → 日勝（無第三段） | 40 ＋ 10 | **50%** |
| 未與日蘇任一方交惡的第三方 | 10 | **90%** |

後端送出的是「累計損失率」而不是「這次扣多少」；前端用
`punishmentBaselines` 記住這條傷害鏈開始前的初始值，每一段都從初始值重算。

## 補查：牌庫操作機制（擋卡／加張／收牌／解鎖）全面實測

### 壞掉的第一個：2.2 柏林密約整張是空的

卡面：「10 回合內所有蘇聯兵員／金錢 perk 功能卡 +2」。實作用的是 `card_copies`，
它直接往 `function_deck` 塞牌——但列強 perk 卡的份數由
`_sync_foreign_deck_cards()` 每次同步時**重算並修回 `desired`**，而同步在每次
關係變動與每回合推進都會跑。所以塞進去的兩張當場就被收走，牌庫從頭到尾都是 2 張。
`applied` 還老老實實回報「card_copies: 2」，看紀錄完全看不出來。

而且卡面寫的是「10 回合內」——`card_copies` 根本沒有時效概念，形狀本來就不對。

**掩護它的那條測試**：`test_treaty_of_berlin_only_supplies_moscows_friends` 斷言
親蘇玩家結束時有 **2 張**，也就是「跟這張卡沒發生過一樣」。它之所以一直是綠的，
正因為這張卡什麼都沒做。

修法：新增 `perk_copy_bonus` payload——不塞牌，而是**抬高該卡的 `desired` 份數**，
於是同步時自己補進來、到期後自己收回去。`_perk_copies()` 現在會把它加進去。
舊測試改成斷言 `base + 2`。

### 壞掉的第二個：從沒打過的仗，登上了報紙

12.19〜12.22 是日蘇開戰的四張戰況報導，標了 `never_drawn`——只能由開戰判定直接
插進 pending，不進牌庫。但它們的標籤是 `[軍事, 戰況]`、`power_note` 是日／蘇，
而 2.4 東方會議是用「日本 [軍事]」**整批加張**的，於是 12.20、12.22 兩張日軍獲勝
的戰報被一起塞進 `event_pool`。

`never_drawn` 原本只在**開局配池**時擋過一次，抽卡迴圈並沒有再檢查。實測：抽出來
了，標題是「日軍守住嫩江防線　蘇軍北撤」——一場從來沒發生過的仗的戰況報導。

修法兩道：`event_pool_add` 比對出來的 id 先濾掉 `never_drawn`；抽卡迴圈自己也加
一道同樣的檢查（任何把卡塞進池子的路徑都繞不過去）。

### 順手補強的一條弱測試

`test_card_copies_really_adds_copies` 只斷言 `applied` 有回報結果，不數牌庫——
這正是柏林密約能瞞過去的原因。改寫成 `test_card_copies_really_lands_in_the_deck`，
把每一張用 `card_copies` 的卡逐張數牌庫，說加幾張就要進幾張。

### 驗證

新增 5 條測試。全套 → **586 項通過**。突變測試：

| 改壞的地方 | 結果 |
| --- | --- |
| `event_pool_add` 不濾 never_drawn（回到原病） | 1 條紅 |
| 抽卡迴圈拿掉 never_drawn 第二道防線 | 1 條紅 |
| `perk_copy_bonus` 不算進 desired（回到空轉） | 3 條紅 |
| `perk_copy_bonus` 永不過期 | 1 條紅 |
| `perk_copy_bonus` 的 `players` 改成 None（人人有份） | **沒咬住** |

最後一項要誠實說明：這是**等價突變**，不是測試的漏洞。柏林密約的
`relation_gate.min` 是 6，而 `_sync_foreign_deck_cards` 判友好的門檻
`FOREIGN_FRIENDLY_THRESHOLD` 也是 6——兩道濾網完全重疊，所以拿掉其中一道，

## 蘇聯側的同一個問題：查了，另外斷了根

### 蘇聯有沒有「沒打過的仗登上報紙」

**沒有，但那是僥倖，不是設計。** 12.19／12.21 兩張蘇軍獲勝的戰報之所以沒被塞進
池子，只是因為資料檔裡剛好沒有「蘇聯 [軍事] 整批加張」這種卡——全部三處
`event_pool_add` 只有 2.4 東方會議是標籤式的，而它指定 `powers: ["日"]`。
換句話說，蘇聯那一半的防線是空的，只是還沒有人去踩。

### 順帶查出來的不對稱

按標籤整批**封鎖**（1.2 昭和改元、3.4 芥川之死封鎖日本 [軍事]）會把 12.20／12.22
兩張日軍獲勝的戰報鎖住，而蘇軍獲勝的兩張不會。實測插入路徑不吃這道鎖
（戰報是直接插進 pending，不走抽卡），所以沒有造成實害——但「日方的戰報被鎖、
蘇方的不會」這件事本身就不該存在。

### 採用的改法：斷根，而不是逐條防守

四張戰況報導的 `tags` 一律清空（原本是 `["軍事", "戰況"]`）。它們只由開戰判定
直接插進 pending，本來就不該落在任何標籤規則的射程內；標籤一拿掉，任何
「按標籤封鎖／按標籤加張」的卡都掃不到它們，日蘇兩側同時免疫。

`power_note`（日／蘇）保留——那只供 README 顯示類別，不參與封鎖比對
（`_event_lock_matches` 沒有 tags 就直接不成立）。`戰況` 標籤全專案沒有任何
程式讀它，清掉無副作用。

實測：2.4 東方會議之後池中四張戰報卡都是 0；1.2／1.5／1.7／2.7／3.4 五張標籤封鎖
之後四張戰報卡都沒被鎖；開戰時蘇軍獲勝、日軍獲勝、以及「日軍獲勝且昭和國喪封鎖
生效中」三種情境各刊 3 則報紙，完全對稱。

### 引擎層的兩道保險仍然保留

資料層斷了根，但不能靠「以後沒有人再把標籤掛回去」。引擎層原本加的兩道
`never_drawn` 過濾（`event_pool_add` 比對結果先濾一次、抽卡迴圈自己再擋一次）
一併留著，並改寫成一條**刻意在記憶體裡把標籤掛回去**的測試——測的是引擎擋不擋
得住，不是資料乖不乖。

### 另外補的一個靜默失敗

`_queue_power_war_reports()` 找不到對應戰報卡時是 `continue`：仗照打、地照易手、
傷害照扣，就是不出報紙，玩家會看到領土無故換手而毫無說明。改成丟 `ValueError`。

從資料檔實算的覆蓋率：日軍地面佔領可能觸及 `['吉林','奉天','江蘇','浙江','黑龍江']`，
蘇軍是 `['吉林','察哈爾','熱河','黑龍江']`，交集正是 `['吉林','黑龍江']`——四張戰報卡
剛好全覆蓋，**目前沒有破口**。但這是算出來的，不是猜的，而且新增一條守門測試
把這份覆蓋率每次從資料檔重算一遍。

### 驗證

新增／改寫 7 條測試，全套 → **594 項通過**。突變測試：

## 買辦技能改制：從「少抽譴責功能卡」改成「機率免疫 [懲戒] 事件卡」

### 舊機制（已整個移除）

`japanese_comprador`（張宗昌）與 `french_comprador`（唐繼堯）原本的免疫作用在
**功能卡**上：對該國關係跌到 −4 以下時，該國的〈某國的譴責〉會塞 3 張進你的
功能卡庫，買辦讓每一張有機率被擋掉（日 10%、法 30%）。結果記在
`state["condemnation_blocked"]`，只在關係惡化那一刻擲一次。

那個機制與「懲戒」毫無關係——譴責卡是無效果的佔位牌。整套拿掉了，
連 `condemnation_blocked` 狀態欄一併刪除，並加一條守門測試防它悄悄復活。
**譴責功能卡本身保留**（照使用者裁示），只是不再受買辦影響。

### 新機制

抽到該國的 **[懲戒] 事件卡** 時當場擲一次。判準是卡片自己的 `tags` 與
`power_note`，所以日後任何一張新的 [懲戒] 卡都自動吃得到，不必回頭改程式。

實際流程（照使用者給的步驟）：

1. 系統抽卡，決定承受者。
2. 承受者持有 `french_comprador`／`japanese_comprador`，且抽到的正是該國的
   [懲戒] → 擲一次技能觸發率（法 30%、日 10%）。
3. **成功** → 靜默重抽，回到步驟 1。玩家不會收到任何通知，也不會有報紙。
4. **失敗** → 直接實施效果並刊報紙。
5. 抽到的不是目標列強的 [懲戒]（別國的、或不帶 [懲戒] 標籤的）→ 直接實施。

### 使用者裁示的四件事

1. 只取消買辦的擋卡機率，**譴責功能卡保留**。
2. 被擋下的卡**留在池子裡**——免疫是「這一次砸不到你」，不是永久免疫。
3. **靜默重抽**，玩家不會知道剛剛躲過什麼。
4. 重抽**設上限 10 次**，達上限就直接實施。

補充一個實作上的必然結果：同一輪裡被擋掉的卡會進 `already`，所以**同一輪不會
對同一張反覆擲骰**——要撞到 10 次上限，得有十張不同的該國懲戒卡連續被擋。

## 買辦機制複查

### 一、暗殺：有機率免疫 ≠ 完全免疫（已補測試）

12.38〈關東軍特務機關行刺〉是日本的 [懲戒]，所以張宗昌的買辦**會**護到它。
但那只是第一層：擋不下來的那 90% 裡，暗殺本身照樣有 20% 成功率。

1500 局實測（奉系持張宗昌，日本發動行刺）：

| 結果 | 次數 | 比例 |
| --- | ---: | ---: |
| 買辦擋下（卡沒降臨） | 140 | 9.3% |
| 降臨但未得手 | 1092 | 72.8% |
| **降臨且得手** | **268** | **17.9%** |

得手率 17.9%，理論值 0.9 × 0.2 = 18%。**張宗昌在手，大帥照樣會死。**
新增兩條測試釘死這件事：一條驗得手率，一條驗「卡片降臨之後，暗殺骰本身
不該被買辦改動」。

### 二、玩家發動的暗殺完全不受影響（已補測試）

〈王亞樵來投〉走 `use_function → _resolve_assassination`，根本不經過抽卡迴圈，
買辦碰不到它。這件事原本只是「讀程式看起來如此」，現在變成會紅的斷言：
同一個 seed 下，有沒有買辦的 `roll`／`chance`／`success` 必須逐一相同（跑 60 個
seed 比對），而且 300 局裡確實打得中有買辦的陣營。

另加一條守門測試：這張卡不能是事件卡、也不能帶 [懲戒] 標籤——哪天有人把它
改成帶標籤的事件卡，買辦就會莫名其妙開始擋它。

### 三、複查找到並修好的兩個洞

1. **複合 `power_note` 比對不到。** `power_note` 允許寫成「蘇／德」這種複數
   （既有的 `_event_powers` 就是這樣解的），但我先前直接拿整串去查表，
   複合寫法一律查不到 → 那種卡**永遠擋不下來**。目前沒有任何 [懲戒] 卡是
   複合寫法，所以還沒炸，是潛在的。已改用同一套分隔符解析。
2. **擋滿上限而放行的那張，被記成「擋下」。** 查帳時會看到同一張卡既被擋下
   又降臨。改成另記一份 `comprador_deflection_overrides`，兩份不重疊。

### 四、複查確認沒問題的

* 全部 32 張 [懲戒] 卡都是 `acknowledge/drawer`（單一承受者），所以擋掉不會
  誤放過別人。
* 技能跟著將領走：張宗昌轉投 S，F 的免疫歸零、S 變 10%。
* 沒有買辦時完全不擲骰（短路），不會擾動亂數序列。
* 非 [懲戒] 的同國事件卡（12.68 法國教案抗議，標籤 [交涉]）80 局全降臨。
* 別國的 [懲戒] 一次都擋不到。

### 五、複查發現、**尚未修**的一個洞（範圍超出買辦，需要裁示）

**陣營層級技能在將領死亡之後仍然生效。**

實測：張宗昌被暗殺身亡之後，奉系仍然享有 10% 的日本懲戒免疫。

這不只是買辦的問題，三個 family 全中：

| --- | --- | --- |

## 前後端連結總複查

### 一、將領死亡的技能洩漏（已修）

前端的 `applyGeneralDeath()` 只把將領在自己的樹上標成 `killed`，**完全沒有回報
後端**。後端的 `faction_general_traits` 只在 `apply_general_join` 時被動更新，
陣亡它收不到消息。三個 family 全中：買辦（免疫列強懲戒）、地方財源（該省每城
+1/+1）、剿共（紅軍起義只需駐一回合）。實測：張宗昌被暗殺身亡後，奉系仍有 10%
的日本懲戒免疫。

修法：`next_turn` 加一個 `faction_trait_holders` 欄位，前端每回合把「技能持有者
還活著、且在哪一家」整份重算交給後端對帳。**用對帳而不是「某某陣亡」事件**——
對帳每回合都會收斂，漏送一次下回合也自己修得回來；`apply_general_join` 造成的
任何漂移也一併修正。沒送這個欄位（舊版前端）就不動它，不會因為漏送而把技能清光。

新增 `FactionTraitReconciliationTests`（9 條），包含前後端技能白名單必須一致的
守門測試——少列一個就等於那個技能永遠不會被回收。

### 二、只動前端、動不到後端的卡（逐張實測）

判準不是讀程式，是**逐張真的打出來，再 diff 後端 snapshot**（`/tmp/card_audit.py`）。
把每張卡必然會動的東西（手牌、棄牌、last_action）排除後，剩下的差異才算數。

89 張功能卡的結果：

| 分類 | 張數 | 說明 |
| --- | ---: | --- |
| 後端狀態確實改變 | 56 | 正常 |
| 打得出但後端零變化 | 10 | 見下 |
| 這組參數打不出來 | 23 | 陣營限制／前置條件，都是正確的拒絕 |

那 10 張逐一查證：

* **6 張是設計上就沒有效果**：五張〈某國的譴責〉與〈中國人之恥〉，卡面明寫
  「無效果」，`mechanic: no_effect`。正確。
* **4 張的效果由前端執行**：〈部隊晉升〉〈鼓吹地方自治〉（忠誠 ±1）、
  〈少帥崛起〉（部隊編制）、〈擴編直屬〉（直屬名額）。這些**不是**漏接——
  後端仍然驗證（絕對忠誠會被擋下）、仍然回傳指令欄位，只是結果狀態住在前端。
  而前端狀態經 `/api/shared-state` 存進伺服器的 `SHARED_TACTICAL_STATE`，
  與 `ENGINE.state` 同樣是伺服器端的權威資料。**兩個都在伺服器上，不是一個
  真、一個假。**

174 張事件卡：只有 11 張 `apply` 碰不到後端。其中 4 張是日蘇戰況報導（純敘事，
已於前次複查確認）、6 張卡面明寫「沒有效果，單純新聞播報」、1 張（2.6 貝爾福
宣言）由前端 `applyFrontendEventEffects` 加忠誠。**沒有一張是漏接的。**

### 三、「後端交辦、沒人執行」的掃描

* `pending_frontend_effects`：卡片會排的 kind（`loyalty_all`、`loyalty_random`）
  在前端都有處理器。→ 無缺口。
* `timed_flags` 的 kind：五種全部有人讀（`silver_reform_done` 是由卡片以
  `immune_flag` 動態指名，程式不寫死字串，改用 `has_timed_flag` 的呼叫點證明）。
* `use_function` 回傳的 26 種欄位：前端全部有讀，除了 `cabinet_entry` 與
  `relation_side_effects`——但這兩者的效果後端**已經套用完了**，前端是從
  `state.cabinet` 與 `foreign_relations` 這兩個權威來源讀的，回傳欄位只是冗餘。
  不是缺口。
* 前端呼叫的 26 個端點全部存在；73 種 `data-*` 觸發器全部有人接（其中 19 種
  是用樣板字串選擇器或純樣式掛勾讀的，逐一確認過）。

### 四、找到並修好的真 bug：**募兵面板顯示的價格是假的**

前端 `renderRecruitmentPanel()` 自己用
`bootstrap.recruit_costs × 陣營費率 + 卡片固定加減` 重算價格，**完全沒有套用
生產成本倍率與限時折抵**。實測：

| 情況 | 面板顯示 | 後端實收 |
| --- | --- | --- |
| 13.1 油價上漲生效中，步兵 | $5／工2 | **$6／工3** |
| 同上，砲兵 | $18／工5 | **$23／工7** |
| 火燒紅蓮寺折抵中，步兵 | $5／工2 | **$4／工2** |

玩家看到 $5、按下去被扣 $6，沒有任何提示。受影響的卡包括 13.1〜13.5 五張經濟
事件，以及既有的英國軍火出口管制、美國禁運案、香港軍火交易、火燒紅蓮寺。

修法：後端在 `snapshot()` 裡發布 `resolved_recruit_costs` 與
`resolved_navy_costs`（呼叫的就是實際扣款用的 `_unit_cost_for`／
`_navy_unit_cost_for`），前端改成直接讀。順手把海軍價格從 `train_navy_unit`
內嵌的算式抽成 `_navy_unit_cost_for`——**算價的地方只能有一處**。

### 五、找到並修掉的潛在分歧：策反的成本與成功率

公式在前後端各寫一份。逐格掃描（忠誠 0–15 × 戰力 0–100，共 128 組）發現
36 組分歧，成因是後端把忠誠夾在 1–10、戰力夾在 ≥1，前端沒夾。實務上碰不到
（前端的忠誠在計算時已夾在 0–10），但公式重複兩份就是遲早的事。已把前端的夾值
改成與後端逐字相同，並加對帳測試掃過整個範圍。

## 戰鬥與忠誠：完整調查，以及忠誠改由後端計算

採用你給的原則：**根本上涉及後端功能、前端只負責呈現的系統，計算只留一份在後端。**

### 一、調查結果：兩套系統的現況

| 系統 | 規則住在哪 | 判定住在哪 | 問題 |
| --- | --- | --- | --- |
| 戰鬥傷害 | `comabt_system/combat.py`（後端） | 後端 `/api/combat` | 無 |
| 戰鬥修正項的組裝 | **前端** `combatTraitModifiers`／`combatAuraModifiers` | 後端吃前端組好的 `modifiers` | 規則在前端 |
| 戰力點 | 後端 `UNIT_FORCE_POINTS`，前端由 bootstrap 讀 | — | 前端有 **5 處寫死的 fallback** |
| **忠誠** | **只有前端** `calculateGeneralLoyalty` | **後端**拿前端算的數字扣錢、擲策反骰 | **規則與判定分居兩處** |

忠誠那一列是最嚴重的：後端完全沒有忠誠計算，卻在 `attempt_defection_with_force`
裡拿前端送來的 `loyalty` 去扣錢並擲骰。規則改在前端，後端不會知道；反過來也是。

### 二、調查中發現的關鍵事實

伺服器**本來就存著**算忠誠需要的全部事實：`SHARED_TACTICAL_STATE` 裡有部隊編制、
將領樹、忠誠覆寫、將領歸屬。後端不是「拿不到資料」，是「沒有人叫它算」。

但有一個實際的斷點：**`tacticalSnapshot()` 的部隊資料裡沒有 `generalId`**。
伺服器手上有部隊、也有將領，卻連不起「這支部隊是誰的」——所以即使想自己算也算不了。
第一次跑對帳時後端把 35 位將領全算成 2（＝判定成沒有部隊），就是這個原因。

### 三、做了什麼

1. **`GameEngine.compute_loyalty()`**：整套規則搬進後端——基礎值、忠誠覆寫、
   列強關係懲罰、在野、無部隊上限 2、相對實力 ±2、戰損 −4 下限、最後夾 0–10。
   回傳值附帶 `breakdown`，讓面板照著顯示而不是自己再推一次。
2. **`GameEngine.loyalty_report(tactical)`**：直接吃伺服器手上的戰術狀態，
   一次算出所有將領的忠誠。
3. **`tacticalSnapshot()` 補上 `generalId`**——修掉那個斷點。
4. **server 在三個回傳 tactical 的地方都附上 `loyalty`**。
5. **前端 `calculateGeneralLoyalty()` 優先採用後端結果**，本地那段算式降級為
   「尚未同步到後端結果時的過渡值」，並在註解裡寫明它不是第二套規則。

### 四、驗證：真前端逐位對帳

用 Playwright 開真前端，把後端結果關掉逼它走本地算式，再與 `loyalty_report`
逐位比對：

| 情境 | 比對將領 | 一致 | 不一致 |
| --- | ---: | ---: | ---: |
| 開局 | 35 | 35 | 0 |
| 打亂局面後（打光一支部隊、加厚一支、關押一支） | 35 | 35 | 0 |

全套 → **717 項通過**。新增 `LoyaltyRulesTests`（12 條）與
`UnitForcePointsSourceTests`（2 條）。突變測試 5 項：

| 改壞的地方 | 結果 |
| --- | --- |
| 無部隊上限 2 改成 3 | 3 條紅 |
| 相對實力不夾 ±2 | 1 條紅 |
| 戰損不夾 −4 | 1 條紅 |
| 前端不採用後端忠誠 | 1 條紅 |
| `tacticalSnapshot` 拿掉 `generalId` | 1 條紅 |

五項全部被咬住。

### 五、順帶釘死的一項

前端有 **5 處寫死的戰力點 fallback**（`{infantry:1, cavalry:1, machine_gun:2,
artillery:4}`）。目前與後端一致，但那是巧合不是保證。加了一條測試把五處全部
與後端的 `UNIT_FORCE_POINTS` 對死。

### 六、一次誠實更正

調查中我一度回報「`DEFECTION_RESISTANCE_TRAITS` 掛的是買辦技能而不是佛教將軍」。
那是**我的抽取工具寫錯**（它抓到了下一個常數區塊），原始碼
`const DEFECTION_RESISTANCE_TRAITS = { buddhist_general: 0.05 };` 一直是對的。

### 七、**戰鬥還沒搬（附理由與計畫）**

戰鬥的修正項組裝仍在前端，我這次**沒有搬**，原因是它需要的事實比忠誠多一層：

* 光環要知道「同一場戰鬥、同一邊有誰」——戰鬥編組住在前端的 `activeBattles`，
  而 `tacticalSnapshot` 有送 `activeBattles`，所以這一項可搬。
* 省份條件（山地師、水域作戰）要知道「這一格屬於哪一省」——地格資料在
  `bootstrap.strategic_map`，後端有，可搬。
* 敵方關係條件（何鍵）要讀對方陣營的列強關係——本來就在後端，可搬。

也就是說**技術上全部可搬**，缺的是把 `AURA_TRAITS`、`PROVINCE_CONDITIONAL_TRAITS`、
`ALLY_PRESENCE_TRAITS`、`ENEMY_PRESENCE_TRAITS`、`ENEMY_RELATION_TRAITS`、
`RELATION_DISABLED_TRAITS` 這六張表從 app.js 搬進後端，並讓 `/api/combat` 自己
組 `modifiers`，前端只送「誰打誰、用什麼戰術」。

我沒有現在動手，因為那會改到戰鬥結算的呼叫介面，影響面比忠誠大得多，
應該由你決定要不要現在做、以及要不要一次做完。

### 八、其他仍未覆蓋的

* 14.9 地方官貪腐的 `loyalty_random` 前端處理器，仍**未在真前端實跑驗證**。

## 海軍：規則搬進後端

### 調查結果

海軍原本的分布是四層裡最極端的一個：

| 項目 | 原本在哪 |
| --- | --- |
| 艦隊規則資料（血量、失能門檻、火力、退卻比例、修理單價） | 後端 `navy_system/data/navy_rules.json`，經 bootstrap 給前端 |

### 搬了什麼

`navy_system/navy.py` 新增六支，與 `frontend/navy.js` 逐條對應：

### 驗證三：測試與突變

新增 `NavyCombatRulesTests`（18 條）。全套 → **752 項通過**。突變測試 6 項：

| 改壞的地方 | 結果 |
| --- | --- |
| 失能門檻由 `>=` 改成 `>` | 1 條紅 |
| 傷害先打運輸船 | 2 條紅 |
| 同類先打血少的 | 1 條紅 |
| 退卻線由 1/2 改成 1/4 | 1 條紅 |
| 對射改成先算傷害再判資格 | 1 條紅 |
| 前端改回本地計算 | 1 條紅 |

**兩項第一次跑逃掉了，兩個原因都要記：**

1. 「對射改成先算傷害再判資格」——我挑的案例裡守方本來就打不動，分辨不出
   同時射擊與循序射擊。補了一條刻意讓守方**挨打之後才掉到門檻以下**的案例
   （守方 16 血，中 10 點後剩 6）：同時射擊會還手，循序射擊不會。
2. 「前端改回本地計算」——我的突變寫成 `{...} && await api(...)`，那仍然會
   呼叫 API，等於沒改到東西。重寫成真的不呼叫才咬得住。

另外查出一個**會誤導判斷的環境問題**：`navy_system/__pycache__` 留著上一次突變
的位元碼，害我一度以為正確的實作也算錯。之後每次突變前都先清 `__pycache__`。
